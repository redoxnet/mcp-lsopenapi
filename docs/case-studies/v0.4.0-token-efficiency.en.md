# v0.4 token efficiency: same question, less context

This case study compares the same seven-turn chart-analysis conversation on
`RedoxNet.Mcp.LsOpenApi` v0.3.0 and v0.4.0 with the same model
(`claude-sonnet-4-6`), host, and LS virtual-market setup.

The result: tool-response payloads dropped from 302 KB to 93 KB including host
discovery probes, and from 259 KB to 46 KB for substantive MCP tool responses
only. The largest single scenario dropped from two chart calls and 58.6 KB to
one chart call and 3.7 KB.

## Setup

| Item | v0.3 | v0.4 |
|---|---:|---:|
| Package | `RedoxNet.Mcp.LsOpenApi@0.3.0` | `RedoxNet.Mcp.LsOpenApi@0.4.0` |
| Model | `claude-sonnet-4-6` | same |
| Market | `LS_MARKET=virtual` | same |
| Host | AssistStudio with inline chart rendering | same |
| Conversation messages | 40 | 38 |
| Tool calls, inclusive | 14 | 12 |
| Tool-response payload, inclusive | 302,365 bytes | 93,419 bytes |
| Substantive MCP payload only | 259 KB | 46 KB |

The inclusive numbers include two AssistStudio `search_tools` discovery probes
at the start of each session. The substantive numbers exclude those probes and
measure only MCP tool responses from this server.

## Hero Scenario

User request:

> Show only Samsung Electronics daily candles from January through June 2024,
> and analyze the MA60 trend inside that same window.

This is a narrow-window plus long-period-indicator problem. A 60-day moving
average needs earlier warm-up bars before the requested display window.

| Version | Calls | Payload | Behavior |
|---|---:|---:|---|
| v0.3 | 2 | 58,636 chars | The model first tried a three-month padded range, noticed MA60 was barely populated, then re-called with `count=190`. |
| v0.4 | 1 | 3,733 chars | The model selected `with_warmup=true` on the first call and received a summary-first display payload. |

v0.3 first call:

```json
{
  "shcode": "005930",
  "period_type": "day",
  "from": "20231001",
  "to": "20240630",
  "indicators": ["ma:5", "ma:20", "ma:60"],
  "include_chart": true
}
```

v0.3 retry:

```json
{
  "shcode": "005930",
  "period_type": "day",
  "count": 190,
  "to": "20240630",
  "indicators": ["ma:5", "ma:20", "ma:60"],
  "include_chart": true
}
```

v0.4 single call:

```json
{
  "shcode": "005930",
  "period_type": "day",
  "from": "20240101",
  "to": "20240630",
  "indicators": ["ma:5", "ma:20", "ma:60"],
  "include_chart": true,
  "output_mode": "display",
  "with_warmup": true
}
```

v0.4 response excerpt:

```json
{
  "dataset_id": "ds_33f114a2",
  "summary": {
    "bar_count": 300,
    "date_range": "2023-04-07 ~ 2024-06-28",
    "moving_averages": {
      "MA5": 81160,
      "MA20": 78565,
      "MA60": 79098,
      "MA120": 76829,
      "MA200": 74480
    },
    "ma60_slope": "flat",
    "coverage": {
      "warmup_applied": true,
      "analytical_bar_count": 300,
      "display_bar_count": 60,
      "note": null
    }
  }
}
```

The display window stays small, while the analytical window has enough warm-up
data. Raw `candles[]` are omitted from `output_mode="display"` and the chart
spec travels through structured content instead of model-facing text.

## The Four Mechanisms

### 1. Summary-first payloads

v0.3 chart responses began with raw `candles[]`, so the model had to read rows
and derive moving-average context, drawdown, divergence, and trend facts.
v0.4 moves the precomputed `summary` block to the front and omits raw candles
unless the caller explicitly asks for export/raw data.

### 2. Warm-up separated from display

`with_warmup=true` lets the tool fetch deeper analytical history while keeping
the requested display window narrow. The model learned this from the tool
description and picked it on the first attempt in the hero scenario.

### 3. Dataset handles for follow-up turns

Follow-up requests such as "add MA200 too" no longer require a full chart
re-query. v0.4 returns a `dataset_id`, and `ls_add_indicator` can reuse the
cached series.

### 4. Coverage notes for self-correction

When an indicator is unavailable, `summary.coverage` can explain why and tell
the model how to recover, for example by re-running with `with_warmup=true`.
The hero scenario did not need that fallback because the first call was already
correct.

## Scenario Results

Payload counts below include only substantive MCP tool responses, not host
discovery probes.

| # | User request | v0.3 | v0.4 | Reduction |
|---:|---|---:|---:|---:|
| 1 | Samsung Electronics daily chart and recent trend | 1 call, 23,299 | 1 call, 3,735 | 6.2x |
| 2 | Add MA200 | 1 re-call, 24,141 | 1 `ls_add_indicator`, 3,855 | 6.3x |
| 3 | Reframe as one year of weekly candles | 1 re-call, 20,617 | 1 `ls_reframe_chart`, 3,619 | 5.7x |
| 4 | Kakao five-year monthly chart with pivots | 2 calls, 20,910 | 1 call, 3,474 | 6.0x |
| 5 | SK Hynix daily, weekly, and monthly | 4 calls, 109,230 | 4 calls, 23,231 | 4.7x |
| 6 | Raw table for the last 10 days | 1 call, 2,469 | 1 call, 4,773 | 0.5x |
| 7 | Narrow Jan-Jun 2024 window plus MA60 | 2 calls, 58,636 | 1 call, 3,733 | 15.7x |

The one regression is scenario #6. It explicitly asked for raw rows, so
`output_mode="export"` included both raw candles and the new summary block.
The absolute increase was small, about 2.3 KB, and is outweighed by the larger
conversation-level savings.

## Methodology

Tool-response bytes are the sum of `conversation.json` messages where
`Role == "Tool"` and `Content` is a string. JSON-RPC envelopes, assistant text,
and tool-use arguments are excluded.

```python
import json, zipfile

with zipfile.ZipFile("LS004.astx") as z:
    conv = json.load(z.open("conversation.json"))

tool_bytes = sum(
    len(m["Content"])
    for m in conv["Messages"]
    if m["Role"] == "Tool" and isinstance(m["Content"], str)
)
```

The `.astx` files are zip archives containing `manifest.json` and
`conversation.json`.

## Why this matters for v1.0

The same pattern now applies beyond charts:

- `ls_get_index_history` defaults to a summary shape and uses export handles for
  large time series.
- `ls_get_stock_info` returns only requested sections by default.
- `ls_holdings_list` can drop quote, industry, or theme detail when the user
  only needs a lightweight portfolio view.
- List/screener tools cap rows with `limit`, while summary fields still report
  full counts where available.

That is the core v1.0 contract: useful market context in chat without forcing
the model to ingest raw market tables unless the user explicitly asks for them.
