# v1.0.0 readiness audit

Date: 2026-05-21

Scope: second-pass audit for the v1.0.0 stabilization release after v0.10.1.
The working tree was clean before this audit. v0.10.1 is the functional v1.0
RC; v1.0.0 should freeze the MCP tool names, model-facing parameter names, and
default response shapes.

## Recommendation

Keep the planned direction, but treat v1.0.0 as a contract-freeze release with
three extra gates:

1. Pin the tool surface, not only response payload sizes.
2. Decide the remaining `top_n` exception before the freeze.
3. Add release-smoke checks for NuGet/MCP Registry packaging.

## Blockers before v1.0.0

### 1. `ls_get_industry_indices` still uses `top_n`

The current plan says all seven list tools use `limit`, but
`ls_get_industry_indices` still exposes `top_n` in code, tests, response echo,
and docs:

- `src/RedoxNet.Mcp.LsOpenApi/Tools/GetIndustryIndicesTool.cs`
- `tests/RedoxNet.Mcp.LsOpenApi.Tests/Tools/GetIndustryIndicesToolTests.cs`
- `README.en.md`
- `src/RedoxNet.Mcp.LsOpenApi/README.md`
- older release-note/spec sections

Decision needed:

- Preferred: rename `top_n` -> `limit` before v1.0.0 and keep the same behavior.
- Alternative: explicitly mark `ls_get_industry_indices` as the lone semantic
  top-N ranking exception and update the v1 plan text.

If the preferred path is chosen, also rename the response echo from `top_n` to
`limit` so response shape and tool schema agree.

### 2. Tool-list token budget was never pinned

SPEC-v0.10 required a `tools/list` token budget gate. Step 3 recorded counts,
but no test currently prevents the frozen surface from silently bloating.

Implemented in this audit:

- `ToolSurfaceFreezeTests` builds a deterministic surface model from the actual
  `[McpServerTool]` registrations.
- It pins the `standard` and `all` profile tool names.
- It token-counts the serialized surface with `cl100k_base`.

Remaining improvement:

- Add a full in-process MCP `tools/list` integration test if the SDK exposes a
  stable test transport or client API. The reflection test is a useful guard,
  but it is not a byte-for-byte SDK schema snapshot.

### 3. Pack/registry smoke should be a release gate

v0.10.1 existed because the MCP Registry rejected the manifest description.
For v1.0.0, add a release-smoke checklist:

- `dotnet test mcp-lsopenapi.slnx -c Release`
- `dotnet pack src/RedoxNet.Mcp.LsOpenApi -c Release`
- inspect the packed `.mcp/server.json`
- verify both manifest `version` fields are `1.0.0`
- verify `mcp-lsopenapi version` prints `1.0.0`
- run `mcp-publisher` dry-run/validate if available

## Test plan

### Added now

- Tool surface exact-name pins for `standard` (32 tools) and `all` (35 tools).
- Catalog trio visibility pin: hidden in `standard`, present in `all`.
- Model-facing row-cap parameter pin for:
  - `ls_get_etf_holdings`
  - `ls_get_top_stocks`
  - `ls_get_high_low_stocks`
  - `ls_get_industry_stocks`
  - `ls_get_theme_stocks`
  - `ls_get_fundamentals_rank`
  - `ls_get_market_warnings`
- Token-budget pins for the serialized tool surface.

### Still recommended

- Real MCP `tools/list` snapshot once a stable test harness is identified.
- Routing eval corpus:
  - structured market-data questions must choose LS tools
  - news/disclosure/rumor/why-moved questions must not choose LS tools alone
  - own-holdings questions must route to `ls_holdings_list`
  - hidden catalog tools should not appear under `standard`
- Core public API baseline if `RedoxNet.LsOpenApi.Core` is also treated as
  stable at v1.0.0.
